Methodology

ShipSafe is a transparent tool. Here is every check it runs, the specific WCAG success criterion each maps to, why that criterion matters for demand-letter risk, and what the tool genuinely cannot see.

What ShipSafe is — and isn’t. It reads your page’s HTML source and runs heuristic checks against WCAG 2.2 and common privacy rules. It flags real, documented risk patterns. It is not legal advice, not a certified WCAG conformance audit, and not a guarantee of compliance. Treat a clean result as “no obvious red flags in the source,” not “certified accessible.”

Accessibility checks (ADA / WCAG)

These seventeen checks map to the Web Content Accessibility Guidelines (WCAG) 2.2 — the technical standard U.S. courts apply when evaluating ADA website claims. They are weighted highest in the overall score because they are the issues automated ADA filers scan for directly.

Check WCAG criterion Why it matters for legal risk
Page language declared 3.1.1 Language of Page
Level A 		Screen readers (JAWS, NVDA, VoiceOver) pick a pronunciation engine based on the lang attribute on the <html> element. Without it, an English page may be read with a French or Spanish voice — making it effectively unintelligible. WCAG 3.1.1 is a Level A requirement, the floor for ADA compliance. Its absence is a quick, defensible strike in a demand letter because it requires a single attribute to fix.
Images have alt text 1.1.1 Non-text Content
Level A 		WCAG 1.1.1 requires every meaningful image to have a text alternative. It is the single most-cited issue in ADA demand letters — often the sole basis for a filing. A missing alt attribute is machine-detectable in seconds, which is why serial filers automate it. Decorative images should carry alt="" to explicitly mark them as presentational; ShipSafe flags any <img> with no alt attribute at all.
Form fields are labeled 1.3.1 Info and Relationships
4.1.2 Name, Role, Value
Level A 		A form input without a programmatic label is unusable by screen readers: the user hears “edit text” with no indication of what to type. Placeholder text does not satisfy this requirement — it disappears on focus and is frequently skipped by assistive technology. ShipSafe checks for a <label for> pointing to the field, an aria-label, an aria-labelledby, or a title attribute. It flags fields that have none of these.
Links & buttons have names 4.1.2 Name, Role, Value
Level A 		WCAG 4.1.2 requires every interactive control to have a name that assistive technology can announce. Icon-only buttons — a close icon with no text, an arrow link with no label — are dead ends for screen-reader users: they hear “button” or “link” with nothing else. ShipSafe checks accessible name computation: visible text, aria-label, aria-labelledby, image alt text, or an SVG <title>. If none is found, it flags the control.
Page has a title 2.4.2 Page Titled
Level A 		The <title> element is announced first when a screen reader loads the page and shown in the browser tab and bookmark. WCAG 2.4.2 requires pages to have descriptive titles — “Untitled” or a missing title leaves users without orientation. It also hurts search visibility, so fixing it serves both accessibility and SEO.
Heading structure 1.3.1 Info and Relationships
Level A 		Screen-reader users navigate pages primarily by headings — they jump from <h1> to <h2> to <h3> to build a mental outline of the page. WCAG 1.3.1 requires that structure conveyed visually be present in the programmatic structure too. ShipSafe checks that exactly one <h1> exists. Multiple <h1> elements (a common AI-builder output) break that outline; zero means there is no navigational anchor at all.
Mobile viewport 1.4.10 Reflow
Level AA 		WCAG 1.4.10 requires content to reflow to a single column at 320px without requiring horizontal scrolling. Without a viewport meta tag, browsers render the page at desktop width on mobile and users must scroll horizontally — making the site practically unusable on a phone. Low-vision users who zoom heavily are particularly affected. The fix is one meta tag.
Main landmark 1.3.1 Info and Relationships
Level A 		A <main> element (or role="main") is an ARIA landmark that lets screen-reader users skip directly to the primary content, bypassing repeated navigation. Without it, keyboard and screen-reader users must tab through every nav link on every page load. It is a one-element fix, and its absence in an otherwise simple page is difficult to justify in a legal context.
Descriptive link text 2.4.4 Link Purpose (In Context)
Level AA 		Screen-reader users often navigate a page by jumping from link to link without surrounding context. WCAG 2.4.4 requires that link purpose be determinable from the link text alone, or from its immediate context. Generic text — “click here,” “read more,” “here,” “more” — tells a screen reader only that a link exists, not where it leads or why. ShipSafe checks for a known list of generic phrases in link text. Links with an aria-label, anchor (#) links, and mailto: links are excluded. The check returns a warning rather than a fail because static HTML context cannot always confirm whether surrounding content makes a link’s purpose clear.
ARIA roles are valid 4.1.2 Name, Role, Value
Level A 		The role attribute tells assistive technology how to announce and interact with an element — “button”, “dialog”, “navigation”, and so on. An empty role="" gives screen readers nothing to work with; an unrecognized value (a typo, a made-up role, or an ARIA abstract role used directly in content) is silently ignored or misinterpreted. ShipSafe checks every element with a role attribute against the full WAI-ARIA 1.2 non-abstract role taxonomy. The check returns a fail because invalid ARIA roles are machine-detectable, straightforward to fix (remove or replace the attribute), and represent a direct failure of the Name, Role, Value requirement that underpins most interactive accessibility.
Tab order preserved 2.4.3 Focus Order
Level A 		WCAG 2.4.3 requires that focusable components receive focus in an order that preserves meaning and operation. tabindex="0" and tabindex="-1" are both safe — they participate in (or are removed from) the natural DOM tab order without disrupting it. A positive tabindex value — tabindex="1", tabindex="2", etc. — is a red flag: it forces focus to jump to those elements before everything else on the page, regardless of DOM order. In practice this nearly always creates a disjointed, confusing keyboard experience for sighted keyboard users and screen-reader users alike. ShipSafe scans the source HTML for any element whose tabindex attribute parses to a positive integer and returns a warning if any are found. The check returns a warn rather than a fail because context matters: a positive tabindex might be an intentional (if unusual) design decision, and visual DOM order cannot be verified from source HTML alone.
Video captions 1.2.2 Captions (Prerecorded)
Level A 		WCAG 1.2.2 requires captions for all prerecorded synchronized audio-video content. A <video> element without a <track kind="captions"> or <track kind="subtitles"> child is inaccessible to users who are deaf or hard of hearing — and it is machine-detectable in the source HTML. ShipSafe checks every <video> element for a caption or subtitle track. The check returns a fail when captions are missing because WCAG 1.2.2 is a Level A requirement with no ambiguity: if the video has audio content, captions are mandatory. If no <video> elements are present, the check returns informational rather than pass, since the absence of video is not a failing condition. Audio-only content (<audio> elements) is not checked here — transcripts for those fall under WCAG 1.2.1, which ShipSafe does not currently check.
Language of parts 3.1.2 Language of Parts
Level AA 		WCAG 3.1.2 is the companion to 3.1.1: where 3.1.1 requires a language declaration on the page, 3.1.2 requires that any passage or phrase in a different language carry its own lang attribute so screen readers can switch pronunciation engines at that boundary. A French quotation on an English page pronounced with English phonology is incomprehensible. ShipSafe checks all elements with a lang attribute other than <html>. Empty lang="" attributes and values that do not conform to the BCP 47 language-subtag format are flagged as a fail — they promise a language context to assistive technology but deliver none. If no inline lang attributes are found, the check returns informational: the page may be monolingual (correctly), or it may have unmarked foreign-language passages that ShipSafe cannot detect from source alone. The check returns a fail rather than a warn because an invalid lang attribute is worse than no attribute — it actively misleads the pronunciation engine.
Skip link resolves 2.4.1 Bypass Blocks
Level A 		WCAG 2.4.1 requires a mechanism to skip blocks of content that repeat across pages — typically a visually-hidden “Skip to main content” link at the top of each page. ShipSafe checks two things: (1) that a skip link exists (detected by class="skip", a class containing “skip-link”, or an anchor link whose text contains “skip”), and (2) that its href fragment points to an element that is actually present in the page source. A skip link that points to a non-existent ID (href="#main" with no id="main" on the page) silently fails keyboard and screen-reader users who activate it — they are deposited in an undefined location rather than skipping the navigation. The check returns info when no skip link is found (the source scan cannot confirm whether one exists above the fold or is injected by JavaScript) and fail when a skip link is present but its destination is missing from the source HTML.
Duplicate IDs 4.1.1 Parsing
Level A 		The HTML specification requires every id attribute value to be unique within a document. Duplicate IDs are a well-known accessibility trap: when a <label for="email"> or aria-labelledby="desc" refers to an ID that appears more than once, assistive technology silently binds to the first matching element and ignores subsequent ones. Form fields get mislabeled, described-by relationships break, and skip-link fragments resolve to the wrong target — all without any visual indication that anything is wrong. ShipSafe collects every id attribute in the page source, counts occurrences per value, and fails on any duplicate. If no id attributes are found, the check returns informational (absence of IDs is not itself a failure). The check returns a fail rather than a warn because duplicate IDs represent a structural HTML conformance error with direct, predictable, and hard-to-detect accessibility consequences.
ARIA required attributes 4.1.2 Name, Role, Value
Level A 		The WAI-ARIA 1.2 specification defines a set of required state and property attributes for certain interactive roles. A role="slider" element must carry aria-valuenow, aria-valuemin, and aria-valuemax; a role="checkbox" or role="switch" must carry aria-checked; a role="combobox" must carry aria-expanded; a role="option" must carry aria-selected. Without these attributes, assistive technology has no way to determine or announce the control’s current state — a slider with no value, a checkbox with no checked state, an option with no selected state. WCAG 4.1.2 (Name, Role, Value) requires that all user interface components expose their state, so a control missing a mandatory ARIA property is a direct 4.1.2 failure. ShipSafe checks each element whose role is in the WAI-ARIA 1.2 required-properties table against those required attributes and returns a fail on any gap. The complete set of roles checked: checkbox, combobox, heading, menuitemcheckbox, menuitemradio, meter, option, radio, scrollbar, slider, spinbutton, switch. The check returns info if no elements with roles requiring mandatory attributes are found — the correct result for static pages that use only semantic HTML without custom ARIA widgets.
Autocomplete on personal-data fields 1.3.5 Identify Input Purpose
Level AA 		WCAG 1.3.5 requires that any input field collecting personal information about the user — name, email, phone, address, password — declare its purpose via the HTML autocomplete attribute. The autocomplete attribute lets browsers and password managers identify the field’s purpose and pre-fill it automatically. For users with cognitive disabilities, motor impairments, or reading difficulties, autofill is not a convenience — it is often the only way they can complete a form accurately and without assistance. Without it, every form requires them to recall and type personal details from memory, which is a significant and unnecessary barrier. ShipSafe checks all <input> elements whose type (email, tel, password) or whose name or placeholder attribute suggests personal information (name, address, phone, zip, city) and flags any that lack an autocomplete attribute. The check returns a warn rather than a fail because WCAG 1.3.5 is Level AA, and because source-only analysis cannot determine whether a custom JavaScript autocomplete mechanism provides equivalent functionality. If no personal-data fields are found in the source, the check returns informational.

Privacy & legal checks

Privacy claims are frequently filed alongside accessibility complaints — they share the same plaintiff’s bar and the same demand-letter economics. These checks are also weighted high in the score.

Check Standard / law Why it matters
Privacy policy linked CCPA / GDPR California’s CCPA and the EU’s GDPR both require a privacy policy if you collect personal data — and “personal data” includes IP addresses and analytics identifiers, not just form submissions. ShipSafe checks for a link whose text or URL contains “privacy.” Its absence is a recurring item in demand letters, particularly when bundled with accessibility claims.
Cookie / consent notice GDPR / ePrivacy Directive Loading tracking scripts (Google Analytics, Meta Pixel, Hotjar, Clarity, Mixpanel, Segment) before a user consents is a direct GDPR violation for EU visitors and a CCPA exposure for California users. ShipSafe checks the source HTML for known tracker signatures and for the presence of a consent management platform or cookie-acceptance banner. If it finds trackers without a consent mechanism, it flags the combination as a fail.
Terms of service linked General legal best practice A Terms of Service link is expected wherever users can register, purchase, or submit content. Its absence is a warn rather than a fail — many simple informational sites have no need for one — but it is a gap worth noting for any site with interactive features.
Contact path General legal / accessibility best practice A reachable contact path — a mailto: link or a page linked as “contact” — matters for both accessibility and legal purposes. Accessibility statements and legal processes require a way for users to report problems. Several state laws and WCAG supplementary guidance specifically encourage providing contact information for accessibility feedback. Its absence is a warn.
Accessibility statement WCAG 2 supplementary / ADA best practice An accessibility statement (a page or section documenting your commitment, known limitations, and a contact for reporting issues) is not a WCAG success criterion, but it is a documented factor in reducing demand-letter risk. Courts and plaintiffs’ attorneys look for evidence of good-faith effort. A statement signals awareness and ongoing commitment; its absence signals the opposite. ShipSafe checks for a link whose text or URL contains “accessib.”

Schema & SEO checks

These checks carry lower legal risk weight, but they are cheap wins — most are single-line fixes with direct visibility impact.

Check Standard What ShipSafe looks for
Structured data (schema.org) SEO / Google Rich Results ShipSafe looks for <script type="application/ld+json"> blocks and attempts to parse each as JSON. A missing block is a warn — Google cannot show rich results without structured data. A block that fails JSON.parse is a fail — it is silently ignored by search engines, so it provides no benefit while looking like it does.
Meta description SEO A <meta name="description"> content attribute with at least some text. It doesn’t affect ranking directly but is your pitch in the search results snippet. Missing it means Google writes one for you, which is usually worse.
Open Graph tags SEO / Social sharing ShipSafe checks for og:title and og:image. Without them, shared links on LinkedIn, Slack, iMessage, and most social platforms show a blank card — a trust signal problem, especially for a business site.
Canonical URL SEO A <link rel="canonical"> tells search engines which version of a URL is authoritative. Its absence is informational on a single-page site — not a problem — but worth noting for sites with URL parameters or multiple paths.

Trust signal checks

These are baseline checks that affect whether a site looks legitimate to browsers and users.

Check Standard What ShipSafe looks for
HTTPS Security / browser policy Checks whether the scanned URL uses the https: protocol. HTTP sites are marked “Not secure” by all major browsers — a visible warning that undermines trust, and a hard barrier to some browser features. Every major hosting platform provides free TLS certificates.
Favicon Browser UI convention A <link rel="icon"> (or shortcut icon) declaration. Its absence is informational — browsers will show a fallback — but a missing favicon is a detail that reads as unfinished, particularly to business users who pin tabs.
No mixed content Security / browser policy On an HTTPS page, any resource loaded over http:// — an image, script, or stylesheet — is “mixed content.” Modern browsers block active mixed content (scripts, iframes) silently and warn on passive mixed content (images). ShipSafe scans src and href attributes in the source HTML for insecure http:// references.

How the score is calculated

Each check returns one of four statuses:

Pass
1.0

Requirement is met.

Warn
0.5

Partially met or a best-practice gap with no direct legal exposure.

Fail
0.0

Requirement is not met. Legal or UX risk.

Info / N/A
—

Not applicable or informational. Excluded from scoring.

A category score is the mean of its applicable checks, multiplied by 100. Health is the mean of the four category scores. The letter grade maps as: A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 55, F below that.

Demand-letter risk is determined by the two legal categories (Accessibility + Privacy), not the overall health:

  • High risk — three or more legal-category fails, or Accessibility score below 50, or Privacy score below 40.
  • Some risk — at least one legal-category fail, or Accessibility score below 85.
  • Low risk — no legal fails and Accessibility score at 85 or above.

Honest limitations

The free ShipSafe check reads the static HTML your server returns. That imposes real constraints:

  • Color contrast is not checked. WCAG 1.4.3 (minimum contrast, Level AA) and 1.4.6 (enhanced contrast, Level AAA) require measuring rendered text against its background. That requires a live rendering environment, not source HTML. Contrast is one of the more common real-world accessibility failures and ShipSafe does not currently catch it.
  • JavaScript-rendered content is invisible. If your site builds its DOM after page load — single-page app frameworks, React, Vue, Svelte — the source HTML may be nearly empty. ShipSafe will analyze what is in the source and flag issues there, but it cannot see the final rendered output. A rendered-DOM scan (using a headless browser) is in development as a planned Pro tier feature.
  • Heuristic matching has false positives and negatives. ShipSafe detects a “privacy policy link” by matching link text or URL against a pattern. A site might have a privacy policy that passes heuristically but is legally inadequate, or might fail the check while having a real policy under an unusual label. The check is a signal, not a certification.
  • One page only. ShipSafe scans the URL you provide. It does not crawl other pages on your site. The homepage scan is a representative sample — your blog posts, product pages, or contact forms may have different issues.
  • Source-HTML accessibility differs from rendered-DOM accessibility. The <main> element, labels, and ARIA roles ShipSafe looks for may differ from what a browser actually constructs if JavaScript moves or replaces elements. Automated testing on the rendered DOM (with tools like axe-core or Lighthouse) will surface issues a source scan cannot.
  • Audio-only content (transcripts) is not checked. WCAG 1.2.1 requires a text transcript for prerecorded audio-only content such as podcasts. ShipSafe does not currently check for <audio> elements or transcript links — only video captions are checked (WCAG 1.2.2).
  • Unmarked foreign-language content cannot be detected. WCAG 3.1.2 requires lang attributes on foreign-language phrases, but ShipSafe can only validate lang attributes that already exist in the source. If a page mixes languages without any inline lang markup, the check returns informational rather than a fail — the absence of markup is invisible to a source scanner.
  • Skip links injected by JavaScript are not visible to the source scan. If a skip link is added to the page by a script after load, ShipSafe cannot detect it. A “no skip link found” result is informational rather than a fail for this reason — it reflects what is in the HTML source, not necessarily what a browser renders.
  • Duplicate ID detection is source-only. ShipSafe detects duplicate id attributes in the HTML source. IDs injected or deduplicated by JavaScript after page load are invisible to the check. A pass result means no duplicates were found in the static source; it does not guarantee uniqueness in the live rendered DOM.
  • ARIA required-attribute detection is source-only. ShipSafe checks whether elements with ARIA roles that have mandatory state/property attributes (per WAI-ARIA 1.2) carry those attributes in the static HTML source. Attributes added or updated by JavaScript at runtime — for example, aria-valuenow on a slider whose value is set by a script — are not present in the source and will be flagged as missing. An info result means no elements with required-attribute roles were found in the static source; it does not guarantee that all ARIA widgets in the rendered DOM are fully attributed.
  • Autocomplete detection relies on field-type and name heuristics. ShipSafe identifies personal-data inputs by checking type (email, tel, password) and matching name or placeholder attributes against a list of personal-information keywords. Custom field names that do not match the pattern will not be flagged even if they collect personal data. Conversely, a field with a matching name that does not actually collect personal information will be flagged. The check also cannot detect JavaScript-based autocomplete widgets that provide equivalent functionality through a custom UI — those fields will be flagged even if the experience is equivalent. A warn result is a prompt to verify, not a definitive finding.
The right place for ShipSafe in a compliance workflow: use it as a fast first pass — a 10-second smoke test before you tackle accessibility properly. A clean result means no obvious red flags in your source. It does not mean certified compliant. If you need a binding determination, talk to a qualified accessibility professional.
